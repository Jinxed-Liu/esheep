# 增重分析重设计方案

日期：2026-09-19  
状态：产品与统计口径设计，尚未实施。仅新增本文档，没有修改 App 代码、数据或云端配置。  
依据：当前本地工作区的页面、分析引擎、称重样本规则、批次与调舍模型；未读取真实牧场数据、未做真机界面验收。下文示例均为虚构演示。

## 1. 设计结论

增重分析应帮助管理者完成三个动作：找到需要关注的群体，判断一批羊在明确区间内的真实增重，追到具体羊只与原始称重记录。

采用三个互斥入口：**全场概览、批次分析、圈舍分析**。全场提供巡查与下钻；批次提供生产评估；圈舍提供在舍期间的表现及当前待处理羊只。单羊详情承接记录核查。

取消全场混合羊群的平均体重趋势。批次内也不能直接连接每次不同参测羊的均重：两次比较必须配对同羊，多轮连续均重趋势必须固定全程参测名单。

## 2. 当前实现为什么难理解

| 当前行为 | 代码核查结果 | 造成的问题 |
| --- | --- | --- |
| 样本范围、圈舍、批次同时显示 | calculateWeight 优先 batchID，再 penID；选中批次后忽略圈舍 | 界面看起来是组合筛选，实际并非交集 |
| 有效羊只 | 显示 eligible 羊只数量，没有要求形成有效称重区间 | 分母包含完全没有体重或只有一次体重的羊 |
| 最新均重 | 每只羊各自最后一次体重的平均，测量日期可不同 | 容易被当成同一天的全群均重；也没有新鲜度提示 |
| 首末 ADG | 每只羊全部可见历史的首末体重差除以天数，再平均 | 不同羊观察起点、时长和阶段不同，难以回答近期表现 |
| 平均体重趋势 | 每个称重日期当天参测羊的体重平均 | 日期之间样本变化可以制造“增重”或“下降” |
| 区间 ADG 趋势 | 各羊相邻区间按终点日期聚合 | 同一天的点可混合不同起点、时长和样本 |
| 圈舍分析 | 先按截止日期的圈舍归属选羊，再取这些羊过去的称重 | 可能把其他圈舍期间的增重归给选中圈舍 |
| 批次分析 | 先筛批次成员有效时间内的称重点，再形成相邻点 | 对退出后重新加入等场景，需要防止跨中断配对 |
| 分析截止时间 | 使用常规称重表最大 occurredAt，而非用户选择的时间范围 | 用户不知道数据截至何日；也未统一覆盖断奶等体重来源 |
| 在群/离场筛选 | 按截止时间之前是否存在移出事件判断 | 不等同于完整的当前或历史状态事实，应接统一状态规则 |
| 趋势线 | 提供线性、对数、指数及二至六次拟合 | 增加选择成本，难以直接回答生产管理问题 |

代码定位：

- `eSheepNext/Features/Workspace/FarmAnalysisCenterView.swift`：WeightGainAnalysisView。
- `eSheepNext/Services/FarmAnalyticsSnapshot.swift`：WeightGainAnalyticsEngine、FarmAnalyticsViewModel.calculateWeight、FarmDeepAnalyticsSnapshotActor、SheepWeightSampleBuilder。
- `eSheepNext/Services/InsightFarmCalculationEngine.swift`：已有完整时间线、连续圈舍区间、统计证据等能力，可评估复用；当前批次归属主要核查端点，不能直接认定已覆盖区间内退出再加入。

这些是当前代码行为，不代表已经证实某个真实牧场发生了相应误算。

## 3. 页面结构

### 3.1 全场概览：先找到值得看的地方

默认时间为最近 30 天，始终展示实际起止日期。这是产品初始观察窗口，不是生物学标准；可以改为本月或自定义。没有足够数据时明确说明，不能偷偷扩大为全部历史。

全场概览按生产批次列出群体；没有人工批次的羊放入“未分批次”，保留进入圈舍分析的入口。不能强制用户补建批次才能使用功能，也不能自动创建业务批次。

首屏依次为：

1. 时间范围与数据更新状态。
2. 数据覆盖：期间对象数、期间称重羊数、可计算增重羊数。各计数按羊只去重。
3. 群体表现列表：群体名称、实际观察日期、平均日增重、可计算数/对象数、体重下降羊数、数据提示。
4. 需要关注：体重下降、低于已设目标、缺少配对称重。可点击名单。

全场不展示一个混合所有用途的“增重成绩”，不默认把繁殖母羊、羔羊、育肥羊排在同一排行榜。按明确用途/阶段分区；无法确认阶段的标为“阶段未明确”，不自行猜测。成年繁殖羊可查看体重变化，但不套用育肥达标评价。

群体默认按名称稳定排列，关注项置于独立区域；选择“按日增重排序”时，仍展示阶段、样本数和观察时间，不据此自动宣称圈舍或饲养方案优劣。

“本期表现”包含期间真实参与的羊，之后出售、死亡或退出批次不应抹去既有表现。待处理名单默认仅展示截至查询时仍在场的羊，离场羊在历史明细中保留。两者标题明确，不使用一个模糊的“在群”开关同时改变所有模块。

### 3.2 批次分析：这一批到底长得怎样

从全场进入时继承时间和筛选；独立进入时先选择批次。批次选择器分进行中、已完成，并展示生命周期日期。

支持两个明确的分析方式：

- **期间表现**：日期范围内真实、合格的相邻称重区间，逐羊汇总后再做群体平均。适合不同日期陆续称重。
- **两次称重对比**：选择两个称重日或明确的称重窗口，只比较两个窗口都有记录的同一批羊。适合整批称重工作。

当前模型未见独立称重轮次实体。初版可将称重日期作为候选，让用户明确选起止；不能把同日全场称重自动当成一次统一生产任务。跨日完成一次称重时，需要用户明确窗口；窗口不能重叠，每只羊在窗口内按公开规则取最后一个有效日称重点。

批次详情排列：

1. 批次名称、用途、分析时间/两次称重日期。
2. 主指标“平均日增重”，单位 g/天；旁边展示有效配对羊只数。
3. 两次称重模式显示同羊起点均重 → 终点均重、平均每只增重、实际间隔；期间模式以平均日增重、区间数和观察天数分布为主，不伪装成统一两次称重。
4. 日增重分布图与体重下降人数；设有适用目标时才显示低于目标/达标人数。
5. 个体明细：耳号、性别、起止日期与体重、天数、日增重、当前状态、归属/数据提示。
6. 历次表现，默认显示各次配对区间的增重柱状图。只有切换到固定样本且确认全轮次都有称重时，才显示连续平均体重曲线。

固定样本模式始终展示“全程均有记录 N 只；排除 M 只及原因”。减少样本后的曲线只能代表该固定样本，不能冒充整个批次。

### 3.3 圈舍分析：在舍表现与当前管理

圈舍分析包含两个名称清楚的内容区：

- **在舍期间增重**：只统计两个称重端点及中间全过程连续在该圈舍的真实区间。转入之前的增重不归该舍；转出又转回的跨舍区间不归该舍；也不按天数估分到各舍。
- **当前在舍羊只**：当前羊只的最近称重、距今时间、需关注名单；可进入单羊完整历史。跨舍增重可在单羊明细看到，但不混入本舍成绩。

同一圈舍有多个批次时，按批次/生产阶段分组显示。批次详情中的“目前在哪个圈舍”作为名单定位条件，不冒充“这个圈舍贡献的增重”。

## 4. 筛选交互规则

| 控件 | 解决的问题 | 规则 |
| --- | --- | --- |
| 全场 / 批次 / 圈舍 | 在分析什么对象 | 三者互斥；切换后不保留不适用的隐藏条件 |
| 日期范围 / 两次称重 | 分析哪段表现 | 明示真实日期；两种模式使用不同但公开的配对规则 |
| 性别、品种、日龄等 | 查看哪类可比样本 | 放在“细分条件”，应用后显示条件摘要和结果数 |
| 已完成批次 | 是否复盘历史生产 | 放在批次选择器，不靠“仅离场”间接寻找 |
| 当前状态 | 定位哪些羊需要处理 | 默认用于名单；若用于统计样本，明确标注为当前存活/在场子样本 |

主页面最多保留对象与时间两层必要选择。日龄筛选按相应区间起点实际日龄，未知日龄单列，不用今天日龄回筛历史；跨阶段区间单列，不分摊成虚构阶段成绩。涉及历史用途时使用可追溯历史事实，无法还原则标未知。

任意页面都用一句话复述当前分析条件，例如：“第八批 · 8月20日至9月19日 · 公羊 · 期间参与样本”。返回上层保留原上下文；清空细分条件恢复当前对象的默认样本，不能切回全场。

## 5. 统计口径

### 5.1 先构建事实，再选择分析区间

1. 从可追溯的实际称重事实构建每只羊的完整时间线，保留记录来源、实际发生日期与 ID。
2. 使用统一的同羊同日统计点规则：当前规则为常规称重优先，其次断奶重、初生重；同来源取当天最后一次。原始记录仍全部可查。
3. 来源明确、日期可靠的初生重与断奶重可以参与相应真实区间；仅有历史兼容字段、缺少可靠发生时间的值，不得虚构成称重点。
4. 先形成原始时间线上的相邻区间，再核查时间、圈舍、批次连续性。不得先删掉不属于所选对象的中间点，再把剩余点拼成新的相邻区间。
5. 默认期间模式要求区间两端均在所选日期范围内；不使用范围外起点、不插值补足边界。跨边界区间列入“未纳入原因”。这会使短时间范围样本少，界面应直接说明。
6. 批次归属要求整个区间连续属于同一且唯一的所选批次。重叠、退出再加入、归属不明分别标记。两次称重对比允许使用选定的两个非相邻端点，但必须核查全过程归属并保留中间事实。

### 5.2 唯一的默认平均口径

单个区间：

`区间日增重（g/天） = （终点体重kg − 起点体重kg） × 1000 ÷ 实际间隔天数`

期间模式对每只羊先汇总所选群体内全部合格区间：

`单羊期间日增重 = 合格区间增重之和 × 1000 ÷ 合格区间观察天数之和`

随后：

`群体平均日增重 = 各有效羊只期间日增重之和 ÷ 有效羊只数`

每只羊在一个群体内一票，避免称重次数多的羊获得更多权重。区间缺口不能计入观察天数。两次称重模式每羊只有一组起止配对，直接逐羊计算后平均。所有界面、名单、导出与 AI 在同一对象/时间/模式下必须得到同一结果；其他历史统计口径需保留明确名称，不能悄悄互换。

### 5.3 两次称重的同羊比较

起点均重和终点均重必须使用相同的 N 只羊。

- 平均增重 kg/只 = 同羊终点均重 − 同羊起点均重。
- 如果每只羊间隔天数不同，不能用“均重差 ÷ 一个平均天数”冒充平均日增重；先逐羊计算。
- 显示实际间隔范围；日增重可计算不代表所有羊经历了相同饲养阶段。
- “群体样本累计增重”不是全场产肉量，首版不放入主指标。

### 5.4 样本数与完整性

- **期间对象数**：所选期间与对象有真实归属交集、符合已显示细分条件的独立羊只数，不是当前存栏数。
- **期间称重羊数**：在相应有效归属内至少有一个有效称重点的独立羊只数。
- **可计算羊数**：至少有一个合格区间的独立羊只数。
- **两次配对羊数**：选定两窗口都有有效记录、且归属核查通过的羊只数。
- **配对覆盖率**：有效配对羊数 / 两窗口及中间全过程都持续属于所选对象、符合条件的羊只数。中途新增、离开者另列，不能伪装成缺称。
- **体重下降羊数**：默认指本期单羊汇总日增重小于 0 的羊只数；“存在下降区间”另作明细标识，避免与期间净下降混为一谈。
- 全场总数按羊只去重；一只羊在不同合法时期可出现在两个群体中，群体计数不能直接相加当成全场总数。
- 同一只羊可以同时有可计算区间和待核查记录。缺口按“羊只数”或“记录/区间数”分别注明，不能把有重叠的原因数相加成总羊数。

### 5.5 数据不足与异常

负增重和零增重都保留，不能删掉来提高均值。日增重小于 0 只表示这段体重下降，不自动诊断疾病。只有一次体重显示“缺少第二次称重”；零记录显示“无称重记录”；零天间隔不计算日增重；没有结果显示“—”而非 0。

明显错误、来源冲突及过短/过长区间应显示“需核查”及记录证据。没有配置的质量规则，不自创生物学异常阈值或静默剔除。根据既有确定性校验不合格的记录不进入正式结果，排除数可查；合法但存疑的记录保留并提示。

“达标”需要用户设置且适用于该用途/阶段/时间的目标；没有目标时只显示分布和体重下降，不显示达标率，也不默认套用统一的 200g 或 300g 标准。逾期复称提醒同样依赖明确的称重计划；没有计划仅显示“距上次称重多少天”。

数据截至日期和同步状态分别显示；未证实同步完成时不能宣称结果为最新云端全量。

## 7. 需要保留、移除和延后的内容

保留：真实称重事实、实际日期、同日去重规则、人工批次与历史归属、单羊追溯、历史已离场羊的生产记录。

从主页面移除：全场平均体重折线、混合各羊终生记录的首末 ADG、线性/对数/高次拟合选择器、无分母的“有效羊只”、互相覆盖的三项筛选。

首版完成：三个入口、明确时间、连续归属配对、逐羊平均、样本覆盖、增重分布、个体名单与来源追溯、缺测状态。

后续能力：固定样本多轮趋势、生产目标与称重计划管理、正式称重任务/轮次、同类批次对比。不能让这些后续能力成为首版看懂数据的前提；尚未支持的目标功能不显示空的“达标率”。正式实施时再核查目标/轮次是否需要新增持久化与云端契约。

## 8. 业务验收案例

1. 第一天称轻羊、第二天称重羊，双方无同羊配对：不能出现增重结果或增长曲线。
2. 同一批次第二次只称部分羊：两侧均重只用同一批配对羊；漏称与中途离组分别说明。
3. 30kg 到 36kg、间隔30天：日增重200g/天，明细可复算。
4. 一只羊称重很多次、一只羊称重两次：群体平均仍逐羊等权。
5. 转入某舍前产生增重：不计入该舍在舍增重；单羊完整历史仍存在。
6. 从某舍转出又转回，两个端点都在该舍：跨中断区间仍不得归该舍。
7. 退出批次后又加入，端点属于同批次：不能跨中断生成有效批次区间。
8. 期间后出售/死亡：历史生产表现保留，当前待处理名单不显示为在场羊。
9. 负增重和零增重：保留真实值，不被正值过滤规则吞掉；不足两次称重用“—”。
10. 同日多来源体重：统计只用统一点，用户能查看被合并记录和来源。
11. 只选近30天但起点在更早：不偷偷跨界补算；显示未纳入原因，可主动扩大日期。
12. 没有人工批次：仍能用全场覆盖与圈舍分析；不自动造批次。
13. 目标未设置：没有伪造的达标率或默认生产标准。
14. 多轮固定样本趋势：每轮完全同羊；无法形成固定样本时解释并返回区间对比。
15. 页面、导出、AI：相同事实、对象、日期、模式和口径得到一致结果。
16. 未知归属/历史状态/同步不完整：明确显示缺口，不用当前状态反推历史。
