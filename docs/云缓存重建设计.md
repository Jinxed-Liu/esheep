# eSheepNext 云缓存重建设计

## 目标与边界

云缓存重建只恢复已激活正式迁移牧场在 CloudKit Development 中的“已确认云端缓存”。它不修改 CloudKit 权威记录，不重复提交迁移数据，不清空未确认 Outbox，也不处理旧版 eSheep+ 或 Supabase。

## 数据流

1. `CloudEngineStateDiskStore` 读取 CKSyncEngine serialization。解码失败时将原文件改名保留，写入 scope 损坏标记，并让该 scope 以关闭自动同步的空 state 启动。
2. `CloudRebuildActor` 为牧场创建会话和独立 `Application Support/CloudRebuild/<sessionID>` 工作区，锁定该牧场写入。
3. `CloudZoneChangeFetcher` 从 `since:nil` 开始分页调用 Zone Changes API，直到 `moreComing` 为 false。
4. 权威操作进入 staging 前验证能力证书、证书撤销状态、设备公钥、操作签名、payload 摘要、operationID 与 revision。成员共享库还必须验证成员快照 generation 不低于 Worker。
5. 照片 CKAsset 下载到 staging 资源目录，逐个验证文件存在、SHA-256 与签名。任何损坏都形成带 recordName 的阻断问题。
6. `CloudRebuildBundleValidator` 校验牧场身份、operationID 唯一性、耳号唯一性、羊只/圈舍/批次/配方/库存/繁殖/备注/照片 UUID 引用。
7. staging 重放业务命令并运行 `FarmHistoryRebuilder`，重建每日存栏、羊天、库存余额、批次区间与当前历史状态。
8. 通过后会话进入 `readyToCommit`。用户提交时，`FarmPersistenceActor` 在单个 ModelContext 事务中清除并替换目标牧场已确认缓存，再按发生时间重放原有未确认 Outbox。
9. 照片写入新的、带 sessionID 的版本目录。事务失败时回滚 SwiftData 并删除该新目录，旧缓存和 staging 均保留。
10. 提交成功后清理旧 serialization，并新建对应 private/shared CKSyncEngine；重置失败时重新锁定牧场，禁止在未知同步状态下继续写入。

## 持久化状态

`CloudRebuildSessionRecord` 持久化 preparing、fetching、downloadingAssets、validating、readyToCommit、committing、completed、failed、cancelled。`CloudRebuildIssueRecord` 保存严重级别、错误码、CloudKit recordName、可解释详情与可选原始载荷。App 退出后仍能审阅失败证据；失败和取消会话可重新执行。

## 不变量

- staging 失败不得改变当前业务缓存。
- 同一 bundle 重复提交不得产生重复 operationID。
- 未确认 Outbox 及其 DomainOperation 不得被旧云端版本覆盖。
- 替换范围严格限定为一个 farmID；账号、设备、证书、绑定、其他牧场与迁移工作区不参与替换。
- 没有合法 Tombstone 的云端删除不作为重建时的合法业务删除。
- 任何较低成员 generation、撤销证书、签名错误、摘要不符或业务引用错误都阻断提交。

## 自动化证据

`CloudRebuildTests` 覆盖替换保留未确认 Outbox 和其他牧场、校验失败回滚旧缓存、同一 bundle 重复提交结果稳定、统一 AppSchema 禁用 SwiftData 自动 CloudKit。引用完整性由共享 validator 同时用于 staging 与提交前二次校验。
